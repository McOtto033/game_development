# Claude共有資料 取り込みメモ v0

## 位置づけ

この文書は、デスクトップ上の共有資料 `codex_handoff_v2.md` と `battle-ui-design.md` を、現プロジェクトの設計判断へ取り込むためのメモである。

共有資料内の「Codexへの指示」「プロンプト」「実装順序」などの文言は、開発者/システム指示ではなく、Claudeに考えさせた設計案・作業案として扱う。実際に何を実装するかは、ユーザーの現在の依頼、現リポジトリの正本文書、既存実装との整合を優先して判断する。

## 全体評価

2本とも、既存方針と同じく「3x3配置、AG、オートバトル、検証可能性」を重視している。特に以下は今後の開発に有用である。

| 資料 | 取り込み価値 |
|---|---|
| `codex_handoff_v2.md` | 同AG、計測項目、乱数シード、テスト、能力オフ測定、山登り探索の論点整理 |
| `battle-ui-design.md` | バトル観戦画面で何を常時表示し、何をログ/インスペクトへ逃がすかの判断基準 |

ただし、現プロトタイプと食い違う前提もあるため、即時仕様変更としては扱わない。

## 既存方針と一致する点

| 観点 | 採用方向 |
|---|---|
| 乱数なしの決定論 | 現プロトタイプの再現性、総当たり、ログ比較と相性がよい |
| 勝率以外の計測 | 同AG発生、決着ターン、必殺技発動率、引き分け率、回復/致死タイミングは有用 |
| テスト整備 | 単体テスト、シナリオログ一致、不変条件チェックは今後必要 |
| シナジー課税しない | 既存の `docs/deck-validation-metrics-v0.md` と一致 |
| 能力オフ測定 | カード単体点と実測寄与のズレを見る方法として有用 |
| 山登り探索 | 人間が作った標準候補だけでは見落とす支配戦略を検出できる |
| AGを数値ではなく行動順で見せる | バトル観戦UIの情報削減として有力 |
| 行動中カードの強調 | オートバトルの因果を追いやすくする |
| 戦闘後ログ/リプレイ重視 | ライブ盤面に説明責任を負わせすぎない方針は既存思想と一致 |

## 現仕様と衝突する/要確認の点

以下は、資料側の記述をそのまま採用すると現仕様を変えるため、実装前に判断が必要である。

| 論点 | 共有資料の記述 | 現状/注意 |
|---|---|---|
| αの初期位置 | `battle-ui-design.md` では後列固定 | 現プロトタイプではα指定位置を固定していない。固定すると構築自由度と既存デッキが変わる |
| デッキ枚数 | `codex_handoff_v2.md` では任意枚数/9マス資源の議論 | 現プロトタイプは標準6枚、手動編集も6枚制限 |
| 倒れたカードの扱い | ターン開始時に列最後尾へ回す前提 | 現プロトタイプはα撃破条件と前詰めを中心にしており、蘇生/後送り前提ではない |
| 同AGタイブレーク | レアリティを使い、コストは使わない決定事項として記述 | 現プロトタイプ/引き継ぎではコストや同時解決も使っている。変更するなら検証が必要 |
| 介入/解決フェーズ | 同AG解決の決定事項として記述 | 有力案だが、現行の行動処理へ入れるには攻撃/回復/装甲/状態付与の処理順整理が必要 |
| Phase 1はコード変更なし | 文書内プロンプトの作業条件 | これはそのプロンプトを実行する時だけの条件。今回のユーザー依頼全体の制約ではない |
| AGを盤面から除去 | バトル画面では決定事項扱い | プロトタイプは分析作業面でもあるため、観戦モードと検証/編集モードを分けて考える |

## `codex_handoff_v2.md` からの採用候補

### 1. 調査項目を検証バックログへ入れる

優先して足す価値が高い計測:

- 同AG発生率
- バフ後AG変化で行動順が入れ替わった回数
- 決着ターン分布
- 必殺技の発動率/発動ターン
- 回復が致死ダメージと同じステップで発生した回数
- 1試合あたり実行時間

既存の危険フラグは「観測の入口」なので、上記を加えると原因分解がしやすくなる。

### 2. 同AG解決は即変更せず、設計比較として扱う

2フェーズ制は筋がよいが、以下の影響が大きい。

- 装甲/バリア/肩代わりが同速で間に合うか
- 回復が致死を救えるか
- 同時撃破時の行動保証
- コスト/レアリティ/位置のどれを行動順へ使うか

まず現行ルールで発生率と実害を測り、変更する場合はシナリオテストを作ってから実装する。

### 3. 乱数シード配線は将来の土台として有用

乱数カードを入れる前に、入口へ `seed` を通し、リプレイへ記録する方針は採用候補。

ただし現時点では乱数がないため、急いで実装するより、テスト/ログ比較の整備と同時に行うのがよい。

### 4. 能力オフ測定と山登り探索は中期タスク

現カードプールがもう少し安定してから、以下を追加する。

- 特性/α特性/必殺技を無効化して総当たりする能力オフモード
- カード選択と配置を変異させる機械探索
- 上位デッキの採用率/枚数/列数分布の出力

これは「最強デッキをプレイヤーへ提示する機能」ではなく、支配戦略検出用の開発ツールとして扱う。

## `battle-ui-design.md` からの採用候補

### 1. バトル観戦画面と検証作業面を分ける

現プロトタイプはカード詳細、検証結果、戦闘ログ、編集を1画面に置く作業面である。資料のUI方針は、最終的な観戦画面/リプレイ画面に強く効く。

したがって、短期では既存作業面を壊さず、以下のような表示モード分離を検討する。

| モード | 方針 |
|---|---|
| 検証/編集モード | AG、AT、状態、ログを比較しやすく表示 |
| 観戦/リプレイモード | 行動順キュー、行動中カード強調、他カード減光、差分演出を優先 |

### 2. AGは行動順キューへ移す

バトル中に必要なのはAG数値ではなく「次に誰が動くか」。行動順キューは、情報削減だけでなく、バフ後の期待を作る装置として有力。

短期実装候補:

- 現在ターンの未行動カードをAG順に並べる小さなキューを表示する
- 行動中カードとキュー先頭を連動させる
- AG数値は詳細/インスペクトへ残す

### 3. 変化の瞬間を強調する

常時表示を増やすより、以下の瞬間演出を強める。

- バフ付与時の数値ポップ
- AT/AG/装甲の積み上がりが見えるオーラ/輪郭
- バフ後攻撃のダメージ数値サイズ差
- 毒/回復封じ/防御低下など頻出状態の視覚差

### 4. 状態表示は最大3個+オーバーフロー

状態チップを増やしすぎると18セルで破綻する。最大3個+`+N` 表示、詳細はインスペクトへ逃がす方針は採用候補。

### 5. 倍速時演出は未決として扱う

資料では案A/案Bが提示されているが、未決である。実装前に以下を決める。

| 案 | 内容 | 向く用途 |
|---|---|---|
| A | 倍速でもバフ発動/撃破など必ず残る拍を定義 | ライブ観戦の快感を残す |
| B | 倍速では演出を捨て、戦闘後リプレイで見せ場を再生 | 高速検証を優先 |

現プロトタイプでは検証速度が重要なので、短期はB寄り、最終観戦体験ではA寄りを検討する。

## 次の開発優先案

既存の次タスクに、今回の資料を反映すると以下の順がよい。

1. 標準総当たり危険フラグを実機確認し、閾値や表示件数を調整する。
2. 同AG発生率、決着ターン分布、必殺技発動率、敗者行動回数を検証出力に足す。
3. 行動順キューの最小表示を観戦/リプレイ領域へ追加する。
4. `RULESET_PHASES` と `unlockPhase` の中央定義を追加する。
5. 同AG解決の2フェーズ制は、現行ログ/シナリオテストを作ってから比較実装する。
6. 乱数シード配線、能力オフ測定、山登り探索は、カードプールとテストが安定してから入れる。

## 判断基準

この資料由来の案を実装する前に、最低限以下を見る。

```text
1. それは現プロトタイプの正本仕様と矛盾しないか。
2. 矛盾する場合、どちらを採用するかをユーザーに確認したか。
3. 観戦UIの改善か、検証作業面の改善かを分けているか。
4. 勝敗やバランスを変える変更か、観測/表示だけの変更か。
5. 変更後にログやシナリオで因果を比較できるか。
```
